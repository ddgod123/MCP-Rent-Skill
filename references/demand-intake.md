# RentPro 需求填写与覆盖细则

在重新领取空白模板、整份模板覆盖或处理复合字段前读取。本文件细化 [SKILL.md](../SKILL.md) 第 3 节，不改变咨询启动、保存成功及搜索就绪门槛。字段以当前 MCP 目录为准，不把示例当默认需求。

## 内容索引

- 3.2：需求字段与会话状态。
- 3.3：首次模板、已填模板与重新填写。
- 3.4：一次 patch 覆盖、增量补填及复合字段示例。
- 3.5：解析、保存与搜索失败的区别。

### 3.2 需求上下文

将需求数据与会话状态分开维护：

**完整咨询需求数据**（只有用户单独选择 `1` 且标准模板已成功返回并展示后，才允许新增或更新）：

- 位置：城市、行政区、商圈、楼盘、通勤目标。
- 物业类型：住宅、别墅或行政公寓。
- 核心筛选：月租预算、居室、面积。
- 时间：计划入住时间、租期。
- 必须条件：用户明确说“必须”“一定要”“只考虑”的条件。
- 可选偏好：用户说“最好”“优先”“有更好”的条件。
- 排除条件：用户说“不考虑”“不要”“排除”的条件。
- 待确认项：用户提到但没有明确是否作为条件的内容。
- 权重：用户明确表达偏好顺序或重要程度时再调整；没有表达时不要擅自制造权重。
- 兴趣房源：用户在完整咨询中点名、追问、索要详情或准备联系的房源引用。

**会话/浏览状态**（不等同于租房需求，不因此创建或更新需求）：

- 联系信息及其授权/承接状态：只有用户明确要求人工联系、核验或约看时，才按第 5 节登记或提交客资。
- 直查队列：当前对话的 `direct_property_queue`（按顺序维护待查楼盘及其“待查/待确认”状态）和当前直查楼盘；
  名称歧义时保留为待确认，只有目标明确且查询成功完成后才移出队列。队列仅由宿主维护，不写入需求版本。
  已有需求时直查沿用其 `session_token`，但不改动需求本身。

同一宿主对话中沿用 MCP 返回的 `demand_id`、`session_token`，不要把它们展示给客户。
新对话按新咨询开始，不查找、询问或复用旧对话的需求标识、令牌或需求内容；
新对话不传旧 `session_token`，由 MCP 生成新会话。同一对话若先直查再建立需求，可以沿用本对话的
匿名浏览令牌。新对话不表示删除后台的历史需求。

在当前对话中明确维护完整租房咨询状态：是否已由用户单独选择 `1`、标准模板是否已成功返回并展示、是否只有空草稿、
是否已有实际需求内容、是否等待重新填写、是否已提交模板待补齐。只有“用户已选择 `1` 且模板已展示”时才允许
需求字段写入；不能仅凭用户早先说过的租房条件、存在空草稿或 `demand_id` 推断咨询已启动。这些是宿主对话上下文，
不是新增 MCP 参数；返回菜单不清除这些进度。

### 3.3 选项 1：开启或继续租赁咨询

本节是完整租房咨询的启动和续接规则。只有按第 2 节确认用户单独选择菜单 `1` 后，才能启动或继续此流程；
自然语言租房意图、单独要求模板或直接发送需求字段都不能替代该启动动作。

1. 首次收到有效的菜单 `1` 时，调用 `start_rental_demand`，不传本轮此前被拒绝的输入或 `snapshot`；
   保留返回的 `demand_id`、`session_token`，展示 `intake_template`。该返回值已是含引导语的完整可发送文本，
   原样展示，不改写、不套代码块、不用本地示例覆盖。在最后一项下方追加 `demand_editor.message`，即
   “定制租房需求请点击 [定制租房需求](服务端返回的 demand_editor.url)”。仅在 `available=true` 且 URL 非空时展示真实链接；
   链接暂不可用时仍展示模板，告知可通过模板或自然语言补充，不伪造链接。只有工具成功返回并实际展示模板后，才标记完整咨询已启动。
   单独的菜单编号不是租房条件，不把 `1` 写入需求字段。
2. 已有需求时，沿用原 `demand_id` 或 `session_token`，调用 `render_rental_demand_template`
   展示当前已填需求，并追加该响应的 `demand_editor.message`；不创建另一份会话，不以空白模板覆盖已有值。
   从其他菜单返回租赁咨询、再次选择 `1` 或要求查看已填模板时，都按此规则续接。
3. 模板保留工具返回的字段顺序、选项、必填标记和已填值，不包在代码块中，不改成复杂表格，
   不重复已经展示过的完整开场介绍。
4. 单独选择 `1` 只表示进入或继续咨询并展示模板，不代表确认需求、立即搜索或同意联系顾问；
   即使已有需求 `search_ready=true`，也不因此自动搜索、确认或提交客资。等待用户继续填写或明确下一步。
5. 用户明确说“重新填一份”“重新填写模板”时，已有需求则仅带原 `session_token` 调用
   `start_rental_demand` 读取空白 `intake_template`，不传 `snapshot`；该调用续接原会话，不更新旧内容。
   只有 `demand_id` 时先用 `get_rental_demand` 取回本对话的令牌；尚无需求则按首次领取模板处理。
   展示空白模板并追加原需求编辑入口；网页仍显示原需求的当前已保存值，不声称网页已被清空。
   等待用户填写回传，不在此时清空、覆盖、确认或搜索，不自动恢复旧字段填入空表。
   用户回传新模板后，按第 3.4 节覆盖原需求；只是再次选择 `1` 不等于要求重新填写。

只有完整咨询已启动且模板已返回后，自然语言租房条件才可作为需求输入保存。启动前的预算、区域、居室等内容
不保存、不缓存、不在用户之后选择 `1` 时补录；用户必须在模板返回后重新提供。首次发送 `1` 只负责启动和展示
模板，不与同一消息中的其他自然语言内容合并成需求条件。

模板和字段以 `start_rental_demand` 返回的 `intake_template`、`basic_catalog`、`required_fields` 为准；
已有需求可用 `get_rental_filter_catalog` 刷新目录。默认必填项是物业类型、租金预算、地段位置、居室，
但不能用固定的“四项齐全”替代服务端 `search_ready` 判断。

- 字段按目录的 `field_code`、类型和选项提交，自然语言录入遵守 `nl_enabled`；`show_in_intake` 决定首次
  模板字段，`web_enabled` 决定网页可编辑字段，不把全部网页字段塞进首轮模板。
- `search_role=record_only` 的字段只记录，不承诺已用于严格筛选；`hard_filter` 是否生效以搜索返回为准。
- 不认识的字段先查目录，不自行创造编码；目录变化或字段校验失败时按第 3.5 节提示并停止，保留用户已表达的
  需求，待用户重新操作时刷新核对，不在失败后自动重提。

模板返回后，用户可以回传模板、用自然语言逐项补充，或点击“定制租房需求”网页填写保存；三种方式等价且可交替使用，
都维护原需求，不强迫一次填完，也不连续追问一长串问题。网页允许保存未齐全草稿，续接规则见第 6.3 节。

如果用户不愿填写模板，一次只追问一个问题。必填未齐时只从 `missing_required_fields` 中选择；基础需求齐全后
按用户意愿补充区域/商圈/楼盘/通勤目标、月租预算上限、居室或面积、计划入住时间、必须与排除条件，
不把可选项变成搜索前提。

### 3.4 需求提交、覆盖与搜索

完整咨询已启动且模板已返回后，用户可通过模板、自然语言或网页填写同一份需求。模板和自然语言按下列步骤保存，
网页保存续接按第 6.3 节处理；三种形式不改变搜索门槛。未启动完整咨询前直接发送模板或需求字段，不构成需求提交；提示用户先回复数字“1”，
且不解析、保存或缓存这些内容。
首次提交指首次提交实际需求内容；领取空白模板时已创建草稿，不应仅凭已有 `demand_id`、
`created` 或版本号就认定为非首次提交。此前已有实际需求内容时，再回传整份模板按覆盖处理。

按以下流程处理：

1. 完整咨询已启动且模板已返回后，读取当前目录，将整份回传内容解析为字段值。若该门槛尚未满足，按本节开头
   提示用户先回复数字“1”，不调用工具。启动后尚无需求时调用 `start_rental_demand`（不得传启动前输入）取得
   会话和目录，再提交当前提交的内容；已有需求则沿用原身份，目录需要刷新时调用 `get_rental_filter_catalog`。
   不把原始模板文字直接当作 `snapshot` 或 `patch`，也不把表格中的数字当作菜单编号。
2. 首次提交且只有空草稿时，将解析出的字段级 `patch` 交给 `update_rental_demand`。
   覆盖提交时，以本次发出的模板所含字段及当前目录为覆盖范围；未领取模板就直接回传时，以当前
   `intake_template` 的字段范围为准。在同一个 `patch` 中通过
   `clear_fields` 清除该范围内的旧值，同时写入新值，使用一次 `update_rental_demand` 完成保存。
   不分成“先清空、再填写”两次写入，也不使用 `start_rental_demand(snapshot=...)` 覆盖已有需求。
3. 整份模板覆盖时，范围内的空白或未填字段保持缺失，不沿用旧值；预算、位置、面积等复合字段
   要整体替换，避免旧预算下限、不限标记、楼盘 ID 或面积边界残留。使用目录允许的字段编码，
   不因覆盖基础模板而清空模板范围外的条件、深度筛选或联系方式。
4. 咨询启动后，用户只说“预算改成三万”等单项修改，或在补齐刚提交模板的缺失项时，使用增量 `patch`，
   保留未提到的字段；不把这些补充当成整份模板覆盖。明确删除字段才用 `clear_fields`。
   未明确的信息不猜测，只有用户明确说“不限”时才记录不限；深度条件仍按第 5 节合并保存。
5. 只有取得明确的保存成功结果，才以返回的新版本 `search_ready` 和 `missing_required_fields`
   决定后续动作。首次提交和覆盖提交都必须重新判断，不能沿用旧版本的就绪状态。
6. `search_ready=false` 时，保存为草稿并只追问缺失的必填项，不搜索、不用旧值补齐。
   保留本次模板提交的找房意图；用户随后补齐缺失项并保存成功后，继续执行下一步。
7. 任何模板或自然语言需求提交、补齐或修改，在保存成功且最新返回 `search_ready=true` 后都自动调用
   `search_listings_by_demand`，除非用户明确要求暂不搜索。不得因输入是自然语言而额外要求“查看结果”；
   使用最新需求版本搜索，不只回复“已保存”，不先要求确认，也不要求用户再次回复数字“1”。
   自动搜索不适用于单独选择 `1`、领取空白模板或只查看已填内容。用户明确确认时才调用 `confirm_rental_demand`。

解析或保存失败时按第 3.5 节停止处理。需要展示当前需求时调用 `render_rental_demand_template`，
网页保存后按第 6.3 节读取最新需求；不以聊天记忆覆盖网页字段。当前产品不提供需求历史浏览或回退服务，
不调用 `get_rental_demand_versions`；内部保存版本继续用于一致性校验。

常用需求结构（字段以当前目录和 MCP 工具契约为准，此处只示意嵌套形状）：

```json
{
  "property_type": "住宅",
  "location": {"keyword": "酒仙桥附近", "district": "朝阳区"},
  "budget": {"max": 50000, "unlimited": false},
  "bedrooms": 4,
  "area": {"min": 300},
  "move_in_time": "两个月内",
  "must_have": ["安静"], "preferred": ["精装修"], "exclude": ["服务式公寓"],
  "pending": [], "weights": {}
}
```

兼容字段 `must_have`、`preferred`、`exclude` 等不替代受控深度筛选目录，也不能仅因已保存就声称严格
命中。需求可先保存为草稿，是否满足搜索前提以服务端 `search_ready` 为准。搜索不要求先调用
`confirm_rental_demand`；只有用户明确接受当前条件或明确说“按这个找”时才调用确认工具。

### 3.5 解析或保存失败

模板或需求内容无法可靠解析、字段校验失败，或 MCP 创建/更新需求失败、超时、未返回明确的
保存成功结果时，统一只提示：

```text
保存失败，请检查网络后重新操作。
```

- 停止本轮后续保存、确认和搜索，不用未保存的新条件查询，也不改用旧需求返回结果冒充本次匹配。
- 不声称保存成功，不擅自补值、清空旧需求或自动反复提交；保留可用的原会话和用户输入，
  等待用户重新操作。保存结果不明时不承诺后台一定未写入，已有本对话需求身份时，重新操作先读取当前需求核对。
- 能解析但必填项留空不属于解析失败，应按第 3.4 节保存草稿并提示补填。
- 已保存成功但房源搜索失败时，不误报“保存失败”；保留需求并提示“房源查询失败，请稍后重试。”。
