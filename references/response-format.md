# RentPro 客户回复格式与口径

本文件是输出契约。处理房源列表、客户链接、详情、比较、收藏结果或缺失数据时按需读取。
事实、统计和链接必须来自 MCP 返回值；不要把本文件的示例占位符当成真实数据。

## 业务楼盘目录

适用于用户询问“你们业务盘是哪些小区”“你们做哪些小区”“目前有哪些豪宅楼盘有出租房源”、选择菜单 `2` 或询问哪些区有业务覆盖。
这不是租房需求搜索，也不是具体楼盘挂牌查询；直接调用 `list_release_properties`，不创建需求、不要求模板、不展示完整开场白。

先说明当前目录是 RentPro 的业务发布范围，不代表全北京全部豪宅楼盘。按区→商圈→楼盘展示表格：

| 楼盘 | 在租套数 | 主力户型 | 参考租金水平 |
|---|---:|---|---|
| {property_name} | {listing_count} 套 / 暂无可展示在租房源 | {primary_layout 或“待运营补充”} | {rent_range 或“待运营补充”} |

- 每个区下按 `business_district` 分商圈；不要把商圈名、户型或租金从楼盘名和地址推断出来。
- `listing_count` 是当前可展示挂牌数；业务范围楼盘可以是 0 套，不能说成全市场无房或当前一定有房。
- `primary_layout` 与 `rent_range` 只使用 MCP 返回的运营确认文案。空值统一写“待运营补充”，不读取或改写 `avg_rent_level` 中的推断/待核实内容。
- 用户问“目前有哪些有出租房源”时可在表格中优先展示套数大于 0 的行，但要说明目录仍包含其他业务楼盘；用户问“你们做哪些小区”时展示全部发布范围。
- 目录后邀请用户直接发送具体楼盘名，随后按“具体楼盘直查”规则调用 `search_listings`；不把目录中的套数当成房源详情，不清空已有需求或直查队列。

## 楼盘条件筛选

适用于用户先筛选楼盘配套或参数，还没有选择具体挂牌的阶段。先调用 `get_property_filter_catalog`，再调用 `search_release_properties`；不创建需求、不要求模板，也不把楼盘结果当挂牌清单。

先简短说明本次条件和覆盖范围，例如“在当前业务发布范围的 {scope_count} 个楼盘中，{matched_count} 个符合全部条件”。按区→商圈→楼盘展示：

| 楼盘 | 符合条件的事实 | 在租套数 | 主力户型 | 参考租金水平 |
|---|---|---:|---|---|
| {property_name} | {matched_facts} | {listing_count} 套 / 暂无可展示在租房源 | {primary_layout 或“待运营补充”} | {rent_range 或“待运营补充”} |

- 只展示 MCP 返回的 `matched_facts`；不要从楼盘名称、开发商、宣传语或其他户型推断命中条件。
- `unknown_count>0` 时说明“另有 {unknown_count} 个楼盘因相关资料待确认，暂未计入符合结果”；未知不等于没有、不符合或全市场无结果。
- 当前在租套数为 0 的符合楼盘仍可展示；楼盘筛选不承诺立即有可租挂牌。
- 用户说“近 5 年内交付的小区”时，使用 `property_params.delivery_date` 的 `within_years=5`；回复中可写“按近 5 年内交付的楼盘筛选”，不要把交付日期改写成单套房源的装修年份。
- 用户说“有地暖的小区”时，使用 `property_params.has_floor_heating`；如果 `unknown_count` 较高，要说明地暖楼盘级资料尚未补齐，不能把缺失说成没有地暖。
- 用户说“五居及以上/多居室的小区”时使用 `house_type.is_5plus_bedroom=true`；用户明确说“450㎡、500㎡、900㎡以上”时使用 `house_type.area` 的数值条件；泛称“大面积”可先按 `house_type.is_300plus_sqm=true`，并说明默认口径为300㎡及以上。
- 用户说“一梯一户的小区”时使用 `house_type.elevator_per_household="1梯1户"`。若用户只说“私密一些”，可以说明按一梯一户这一可核验户型方向筛选；不能把结果说成管理严格或整盘所有户型都一梯一户。
- 户型条件结果读取 `matched_house_types`，写成“该楼盘有符合条件的户型”；多个户型条件必须由同一户型满足。不要把楼盘的总在租套数说成这些户型的在租套数。
- 用户提出待治理条件时，明确说“当前暂不能按该条件严格筛选”，不要静默忽略，也不要把开发商当物业公司或把单户型梯户比当作全盘事实。
- 结果后可以询问用户想继续了解哪个楼盘；只有明确要求看该楼盘的在租房源时，再转到挂牌直查。

## 首轮房源列表

本节适用于标准需求搜索；具体楼盘直查使用下一节，不展示全量跨楼盘聚合表。
回复顺序固定为：

1. 有效期提示；
2. 当前租房需求；
3. 全量命中概览和楼盘聚合表；
4. 返回结果中第一个楼盘的全部匹配挂牌；
5. 深度筛选入口（仅 MCP 返回 `deep_filter` 时）。

标准模板：

```text
### 当前展示房源的有效期为：**{从 search.validity_notice 原样取出的日期}**

一、当前租房需求
{只列当前已知的物业类型、预算、地段、居室、面积等基础条件}

二、在租房源
共匹配到 {search.district_count} 个区，{search.property_count} 个楼盘，{search.total} 套房源

楼盘列表：

| 序号 | 区 | 商圈 | 楼盘 | 套数 | 楼盘资料 |
|---:|---|---|---|---:|---|
| ① | {district} | {business_district} | {property_name} | {count} | [楼盘资料]({property_url}) |

三、首个楼盘的在租房源
按“区 → 商圈 → 楼盘 → 房源”分组；`list` 模式中的首个楼盘挂牌不得再次截断。

### {区}
#### {商圈}
##### {楼盘}

①标题：{listing.title}
{楼盘}｜{户型/居室}｜{面积}｜{月租}｜[查看房源详情与笔记]({note_url})

四、继续筛选
请打开 MCP 返回的 `deep_filter.url` 修改条件。保存后回到当前对话回复“已保存”，我会按最新需求重新查询。
```

硬规则：

- `validity_notice` 放在楼盘聚合和房源列表前；日期原样使用，不说成锁定或保证可租。
- 统计必须使用 `district_count`、`property_count`、`total` 的全量命中值，不能用正文展示条数代替。
- `property_groups` 按 MCP 返回顺序渲染，不从挂牌正文重新猜区、商圈、楼盘或套数。
- `list` 模式的 `listings` 已是首个楼盘的全部匹配挂牌；不要再次截成 5 套。
- 房源和楼盘序号使用 `①②③` 等带圈数字；阿拉伯数字 `1`–`9` 只用于快捷菜单。
- 位置优先使用 `listing.location.district` 和 `listing.location.business_district`；缺失写“待补充”，不从地址或楼盘名推断。
- 不主动添加顾问式排名、交通百科或长篇推荐理由；只有用户明确要求时才进入比较/顾问模式。

## 具体楼盘直查

一次只展示当前楼盘，不要求模板，不把查询写成已建立或已修改的需求。
`search_listings` 直接返回 `validity_notice`、`property_groups` 和 `listings`，没有外层 `search`。
单楼盘命中时，使用返回的 `property_groups[0].property_name`、`listing_count` 和 `property_url`，
展示该楼盘的全部 `listings`，不再截成 5 套；每套的楼盘必须与当前组一致。

```text
### {validity_notice}

### {property_name} 当前在租房源
共找到 {listing_count} 套当前可展示房源
[楼盘资料]({property_url})

①标题：{listing.title}
{property_name}｜{户型/居室}｜{面积}｜{月租}｜[查看房源详情与笔记]({note_url})
```

- 用户本次明确附加了预算或居室等条件时，简短写明本次筛选，不引用未要求沿用的旧需求。
- 有待看楼盘时末尾提示：“回复‘下一个’查看下一个楼盘，也可以直接发送具体楼盘名称。”
  队列已全部看完时说明已看完，可直接发送其他楼盘名称，不再提示存在“下一个”。
- `property_count>1` 说明名称有歧义，只列 MCP 返回的楼盘名称让用户确认；不要展示跨楼盘挂牌，
  也不要把总数当成用户指定楼盘的套数。确认完整名称后重新查询。
- `total=0` 时说明“该楼盘在当前发布范围内暂无可直接展示的在租房源”，不是“全市场无房”；
  不自动换楼盘、不删除用户条件重搜。零结果仍算本轮已查询，用户可以继续“下一个”。
- `session_token` 仅供宿主续接查询、收藏/排除，不向客户展示，不代表已创建需求。
- 客户链接、有效期、带圈序号和缺失字段继续遵守本文件的通用规则；无链接时不输出示例占位链接。

## 客户链接

### `note_url`

- 只有 MCP 返回真实 `note_url` 时才显示“查看房源详情与笔记”链接。
- 不把 `listing_ref`、数据库 ID、后台地址或七牛原始资源地址改写成客户链接。
- 链接打开后继续追问，仍回到 `get_listing_detail`；页面内容不等于实时锁定承诺。
- 为空时可写“房源笔记页面正在准备”，不要输出占位链接。

### `property_url`

- `property_groups[].property_url` 有值时原样显示为“楼盘资料”链接；不自行拼域名、路由、楼盘 ID 或 token。
- 为空时写“楼盘资料暂不可用”；失效时说明需要重新获取，不沿用旧 token。
- 楼盘页的在租列表不是当前需求的匹配结果，不承诺每套都符合预算、居室或面积条件。
- 缺参数、户型图或交通信息时保留“待补充/待确认”，不把缺失解读为没有。

## 详情、比较和选择结果

- 详情：先回答用户问的字段；问照片、户型图或笔记时先给对应内容，不借机展开整套楼盘百科。
- 比较：只比较用户选定的 2–5 套；先给结论，再列匹配点和取舍，未知字段标“待确认”，最后给下一步。
- 收藏/排除：先调用 `get_rental_listing_selections`，不要重新搜索或凭聊天记忆猜测。默认“选中的房子”为
  `state=favorite`，明确说排除时用 `state=excluded`；为空时明确说当前会话没有对应记录。

收藏结果示例：

```text
### 你刚才收藏的房源

①标题：{标题}
{楼盘}｜{户型/居室}｜{面积}｜{月租或待确认}｜[查看房源详情与笔记]({note_url})

如果需要，我可以把你收藏的房源整理后交给房源经理进一步核验。
```

## 缺失和禁止展示

服务端有 `missing_text` 时优先使用服务端文案；没有时使用以下兜底：

- 租金缺失：这套房源的租金目前待房源经理确认。
- 户型图缺失：该户型的户型图暂缺，小编正在补充。
- 照片缺失：目前暂无可展示照片，房源经理可以进一步核验。
- POI、交通或楼盘参数缺失：这部分信息暂待补充/确认。
- 没有挂牌：当前发布范围暂时没有可直接展示的在租房源；如果你愿意，我可以把需求转给房源经理人工核验。

不得展示：

- `listing_id`、`listing_ref`、`lead_id`、`session_token`、数据库 ID；
- `source`、`confidence`、`evidence`、`basis`；
- `lifecycle_status`、`governance_status`、同步批次、生产库、镜像库、metadata；
- 内部推算、审核过程、后台人员和内部备注；
- 未经 MCP 明确返回的交通距离、车程、价格推导或户型特征。

缺失不等于不存在；不得用占位图、其他户型图、房源照片或来源页代替真实资料。
