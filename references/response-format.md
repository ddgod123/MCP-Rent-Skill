# RentPro 客户回复格式与口径

本文件是挂牌输出契约。处理标准需求搜索、具体楼盘直查、客户链接、详情或缺失数据时读取。
事实、统计和链接必须来自 MCP 返回值；不要把本文件的示例占位符当成真实数据。

## 输出范围与表格

业务楼盘目录和楼盘条件筛选改读 [楼盘结果格式](property-results.md)，不套用本文件的需求摘要。每个结果集只用一个表头，单元格不换行、不含未转义竖线；保留规定列和缺失占位，不用未选条件补表。

## 完整咨询的每次房源搜索结果

本节适用于标准需求搜索；具体楼盘直查使用下一节，不展示全量跨楼盘聚合表。
回复顺序固定为：

1. 有效期提示；
2. 当前租房需求；
3. 全量命中概览和楼盘聚合表；
4. 按区→商圈→楼盘展示全部匹配挂牌；
5. 定制需求入口使用 `demand_editor`；在楼盘资料右侧展示，零结果或没有楼盘链接时独立展示，不重复堆叠入口。

标准模板：

```text
### 当前展示房源的有效期为：**{从 search.validity_notice 原样取出的日期}**

一、当前租房需求
| 需求项 | 当前需求 |
|---|---|
| {demand_summary[].label} | {demand_summary[].value；status_label 非空时附上该说明} |

二、在租房源
共匹配到 {search.district_count} 个区，{search.property_count} 个楼盘，{search.total} 套房源

楼盘列表：

| 序号 | 区 | 商圈 | 楼盘 | 套数 | 资料与需求 |
|---:|---|---|---|---:|---|
| ① | {district} | {business_district} | {property_name} | {count} | [查看楼盘资料]({property_url}) [定制租房需求]({demand_editor.url}) |

三、在租房源明细
按“区 → 商圈 → 楼盘 → 房源”分组；`list` 模式的挂牌明细覆盖全部命中楼盘。

### {区}
#### {商圈}
##### {楼盘}

①标题：{listing.title（静默删除房号、单元号、楼栋号、门牌号等隐私；若标题只剩隐私信息，则使用“{楼盘}｜{户型/居室}”作为标题）}
{楼盘}｜{户型/居室}｜{面积}｜{卫浴信息（MCP 有值时）}｜¥{金额}/月｜[查看房源详情与笔记]({note_url})

需要调整条件时，请点击“定制租房需求”。保存后回到当前对话回复“已保存”，我会读取最新需求继续匹配。
```

硬规则：

- `validity_notice` 放在楼盘聚合和房源列表前；日期原样使用，不说成锁定或保证可租。
- 每次完整咨询搜索都在有效期下方、命中概览上方展示 `demand_summary` 表格，包括后续重查和零结果。
  仅使用本次返回的摘要，不从聊天记录拼字段，不混用其他版本。空值、未选择和未勾选项不显示；
  明确的“不限”、否定、排除条件是有效需求，不能当空值删去。`status_label` 非空时随条件展示，防止把仅记录条件说成已筛选。
  用户文本中的竖线和换行应转义为适合表格的显示形式，不改变条件含义。
- `demand_editor.available=true` 且 URL 非空时才展示“定制租房需求”；同一结果中所有入口使用同一份需求链接。
  缺少楼盘 URL 时省略该楼盘资料链接，保留编辑入口；零结果时单独提供编辑入口。
- 兼容旧响应只返回 `deep_filter` 时可将其显示为“定制租房需求”；不得猜测链接或同时显示两个重复入口。
- 统计必须使用 `district_count`、`property_count`、`total` 的全量命中值，不能用正文展示条数代替。
- `property_groups` 按 MCP 返回顺序渲染，不从挂牌正文重新猜区、商圈、楼盘或套数。
- `list` 模式的 `listings` 已是全部匹配挂牌，数量与 `total` 及 `property_groups[].listing_count` 使用同一全量口径；不要再次截成 5 套。
- 标准需求搜索和楼盘直查均按 MCP 返回的全量挂牌口径展示，不自行截断。
- 房源和楼盘序号使用 `①②③` 等带圈数字；阿拉伯数字 `1`–`9` 只用于快捷菜单。
- 房源列表后如需提示用户查看内容，直接引导点击对应的“查看房源详情与笔记”链接；楼盘层面的资料、配套或周边信息引导点击“查看楼盘资料”链接。带圈序号仅作条目标识，不得写成“回复/说看第⑥套详情”等需要用户再输入序号的操作。
- 每套挂牌必须严格使用两行格式：第一行是“①标题：……”；第二行依次是“楼盘｜户型/居室｜面积｜卫浴（有值才显示）｜¥金额/月｜[查看房源详情与笔记](真实 note_url)”。不得把两行合并成一行，不得改成“查看房源”或裸露 URL。
- 若提供菜单入口，写“回复数字‘1’开启完整咨询”或“回复数字‘6’获取房源经理联系方式”，不要只写“回复 1/6”。菜单 `6` 先调用 `get_manager_contact` 获取联系方式，不代表已代为登记核验或约看；如需登记承接意向，应邀请用户直接说明并按 `request_viewing` 处理。
- 位置优先使用 `listing.location.district` 和 `listing.location.business_district`；缺失写“待补充”，不从地址或楼盘名推断。
- 房号、单元号、楼栋号、门牌号及其他可定位到具体住宅单元的信息绝不展示，也不向客户索取。隐私处理必须静默执行，不解释字段过滤、隐私处理或链接承载方式；标题含有隐私时仅删除隐私片段并保留标题行。房源详情链接使用短 Markdown 标签，不直接裸露长 URL。
- 不主动添加顾问式排名、交通百科或长篇推荐理由；当前不提供顾问式多套推荐、房源比较、优缺点分析或跨房源排序。

## 标准需求无结果

本节仅适用于 `search_listings_by_demand` 返回 `total=0`；具体楼盘直查和楼盘条件筛选分别使用本文件对应的零结果口径。

- 说明“当前发布范围没有严格匹配的可展示挂牌”，并按当前需求版本展示或复述已确认条件；不得以旧版本、聊天记忆或自行放宽后的条件替代。
- 只有 MCP 返回 `relaxation_options` 时才展示最多 1 至 2 项；不得自行推断需要放宽的条件。用户明确同意后才更新需求并重新搜索。
- 只有 MCP 返回 `lead_fallback.recommended=true` 时，才依据其 `reason`、`next_step` 和 `questions` 邀请用户考虑人工核验；不因零结果自动调用 `request_viewing`。
- 工具错误、解析失败或缺少 `total` 不按零结果处理。

## 已有结果的后续追问

首轮结果已经展示后，用户询问单套房源的事实（如面积、租金或户型）时，直接基于当前仍有效的返回结果回答，
只展示与问题相关的字段，不重复完整概览和全部挂牌。用户明确要求刷新、需求发生变化或结果已过有效期时，
才按当前最新需求重新调用搜索。用户要求多套比较、优缺点分析或跨房源排序时，说明当前版本暂不提供该服务；可引导其打开各套房源详情链接，或联系房源经理。

## 具体楼盘直查

一次只展示当前楼盘，不要求模板，不把查询写成已建立或已修改的需求。
`search_listings` 直接返回 `validity_notice`、`property_groups` 和 `listings`，没有外层 `search`。
单楼盘命中时，使用返回的 `property_groups[0].property_name`、`listing_count` 和 `property_url`，
展示该楼盘的全部 `listings`，不再截成 5 套；每套的楼盘必须与当前组一致。

```text
### {validity_notice}

### {property_name} 当前在租房源
共找到 {listing_count} 套当前可展示房源
[查看楼盘资料]({property_url})

①标题：{listing.title（静默删除房号、单元号、楼栋号、门牌号等隐私；若标题只剩隐私信息，则使用“{property_name}｜{户型/居室}”作为标题）}
{property_name}｜{户型/居室}｜{面积}｜{卫浴信息（MCP 有值时）}｜¥{金额}/月｜[查看房源详情与笔记]({note_url})
```

- 用户本次明确附加了预算或居室等条件时，简短写明本次筛选；不得引用或暗示未要求沿用的旧需求条件已参与本次直查。
- 有待看楼盘时末尾提示：“回复‘下一个’查看下一个楼盘，也可以直接发送具体楼盘名称。”
  队列已全部看完时说明已看完，可直接发送其他楼盘名称，不再提示存在“下一个”。
- 用户想查看某套房源的照片、户型图或挂牌详情时，指引点击该套对应的“查看房源详情与笔记”链接；想查看楼盘资料、配套或周边信息时，指引点击“查看楼盘资料”链接。不要让用户通过输入带圈序号打开详情。
- `property_count>1` 说明名称有歧义，只列 MCP 返回的楼盘名称让用户确认；不要展示跨楼盘挂牌，
  也不要把总数当成用户指定楼盘的套数。确认完整名称后重新查询；若该名称来自待看队列，澄清期间保留该队列项。
- `total=0` 时说明“该楼盘在当前发布范围内暂无可直接展示的在租房源”，不是“全市场无房”；
  不自动换楼盘、不删除用户条件重搜。零结果仍算本轮已查询，用户可以继续“下一个”。
- `session_token` 仅供宿主续接查询或需求，不向客户展示，不代表已创建需求。
- 直查不展示个人 `demand_summary` 或“定制租房需求”链接，即使当前会话另有完整咨询需求，也不暗示旁路结果符合它。
- 客户链接、有效期、带圈序号和缺失字段继续遵守本文件的通用规则；无链接时不输出示例占位链接。

## 客户链接

### `note_url`

- 只有 MCP 返回真实 `note_url` 时才显示“查看房源详情与笔记”链接。
- 房号、单元号、楼栋号、门牌号及其他可定位到具体住宅单元的信息属于隐私，绝不在列表或详情中展示，也不主动索取。隐私处理静默执行，不解释字段过滤、隐私处理或链接承载方式；标题含有此类信息时仅删除隐私片段并保留标题行。不要把房源详情长 URL 作为裸文本输出。
- 不把 `listing_ref`、数据库 ID、后台地址或七牛原始资源地址改写成客户链接。
- 链接打开后继续追问，仍回到 `get_listing_detail`；页面内容不等于实时锁定承诺。
- 为空时可写“房源笔记页面正在准备”，不要输出占位链接。

### `property_url`

- `property_groups[].property_url` 有值时原样显示为“查看楼盘资料”链接；完整咨询结果右侧可并列当前 `demand_editor` 的“定制租房需求”。不自行拼域名、路由、楼盘 ID 或 token。
- 为空时写“楼盘资料暂不可用”；失效时说明需要重新获取，不沿用旧 token。
- 楼盘页的在租列表不是当前需求的匹配结果，不承诺每套都符合预算、居室或面积条件。
- 缺参数、户型图或交通信息时保留“待补充/待确认”，不把缺失解读为没有。

房源结果后的操作引导应使用本次结果中实际存在的链接：单套挂牌内容通过对应的“查看房源详情与笔记”链接打开，楼盘资料通过“查看楼盘资料”链接打开。链接为空或未返回时，不要承诺点击可查看，也不要用房源序号替代链接入口。

## 详情

- 详情：先回答用户问的字段；问照片、户型图或笔记时先给对应内容，不借机展开整套楼盘百科。
- 实体距离为 `distance_kind=straight_line` 时写“直线约 X 米”，保留 `distance_notice` 的边界；不写成步行距离。地铁/环线缺失按待确认处理，不拿旧回答补齐，不推算地铁线路或步行时间。
客户对房源感兴趣时，引导其直接提出核验、联系房源经理或约看请求；只有用户明确提出人工承接或同意登记联系方式后，才按 `request_viewing` 流程处理。

## 缺失和禁止展示

服务端有 `missing_text` 时优先使用服务端文案；没有时使用以下兜底：

- 租金缺失：这套房源的租金目前待房源经理确认。
- 户型图缺失：该户型的户型图暂缺，小编正在补充。
- 照片缺失：目前暂无可展示照片，房源经理可以进一步核验。
- POI、交通或楼盘参数缺失：这部分信息暂待补充/确认。
- 没有挂牌：按查询类型使用本文件的零结果口径；只有 MCP 返回并明确建议人工核验时，才邀请用户提交给房源经理核验。

不得展示：

- `listing_id`、`listing_ref`、`lead_id`、`session_token`、数据库 ID；
- `source`、`confidence`、`evidence`、`basis`；
- `lifecycle_status`、`governance_status`、同步批次、生产库、镜像库、metadata；
- 内部推算、审核过程、后台人员和内部备注；
- 未经 MCP 明确返回的交通距离、车程、价格推导或户型特征。

缺失不等于不存在；不得用占位图、其他户型图、房源照片或来源页代替真实资料。
